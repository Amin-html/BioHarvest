# ADR-008: Payment abstraction — интерфейс PaymentProvider, MVP = Cash on Delivery

**Context**: локальный (кыргызский) payment-провайдер ещё не выбран,
но архитектура не должна блокировать его подключение позже.

**Decision**: ввести интерфейс `PaymentProvider` с методами
`create_payment / verify_payment / handle_webhook / refund`; в MVP
единственная реализация — `CashOnDeliveryProvider` (без реального
внешнего вызова, просто помечает заказ как "к оплате при получении").

**Reason**: Order/OrderStatusHistory не завязаны на конкретного
провайдера — при подключении реального провайдера меняется только
реализация интерфейса и добавляется webhook-эндпоинт, ядро заказов не трогается.

**Trade-offs**: интерфейс проектируется "вслепую" без реального провайдера
перед глазами — есть риск, что реальный провайдер потребует полей, которых
интерфейс не предусмотрел (например, специфичный 3D-Secure redirect flow) —
это будет уточнено при выборе провайдера в Future-фазе.
